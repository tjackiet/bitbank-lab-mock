# 受け取る前に確認してほしいこと（Plan A）

## 1. この文書は何か

**利用側がこのモックを実験環境として受け取る前に、目を通して合意しておきたい点の索引である。**
読む人は、このモックの上に自分たちの層を実装する実装担当と、その設計をレビューする人。
読む時期は、実装に入る前——ここで挙げた項目は、後から気づくと利用側のコードの書き直しになる。

判断してほしいのは次の 3 つ。

1. **推測で決めた挙動**（3 節）を、そのまま前提にしてよいか。実 API と違っていたときに困る箇所はどこか
2. **未確定として残した論点**（4 節）のうち、先に決めないと進めないものはあるか
3. **未実装・保証しない領域**（5 節）が、実験の範囲と衝突しないか

**この文書は挙動を説明しない。** 挙動の正は [`fidelity.md`](fidelity.md)（モック挙動の対応表）で、
ここはそこへの導線と、どこを見てほしいかの優先順だけを持つ。
説明を写すと必ず片方が古くなるので、意図的に写していない。

**このモックは bitbank 公式のテスト環境ではない。** 公開ドキュメントに準拠した近似で、動作保証はしない。
位置づけと免責は [`README.md`](../README.md) を見ること。

## 3. 確認してほしいこと（推測で決めた項目）

[`fidelity.md`](fidelity.md) の対応表は、**小節ごとに「推測」の行を持つ**。ここに全部は挙げない——
写せば対応表の複製になり、片方が古くなる。**どれが推測かはその行で読める**ので、
範囲を自分で確かめたいときは対応表を読むこと。

**選んだ基準**: 次のどれかに当たるもの、つまり**推測が外れていたときに利用側のコードを書き直すことになる**もの。

- (a) 応答の**形**（フィールドの有無・型・桁）を前提にした処理が壊れる
- (b) **error code による分岐**が変わる
- (c) **残高・拘束額の見積もり**が変わる
- (d) 実 API と**符号や向きが逆**になりうる

選から漏れたものは対応表の各小節を見てほしい。基準に当たらない推測（`/_control/` の設計判断など、
そもそも本番 API に存在しない口についてのもの）は、利用側の設計に影響しない。

### 残高と発注可能量の見積もり（基準 c・d）

- [拘束額](fidelity.md#拘束額) — 拘束額に手数料が乗る向きは、実 API を 1 回測った範囲でモックと一致して見えた。
  **推測として残るのは、その 1 回の観測をペアや注文種別へ広げることと、料率の側**
- [手数料](fidelity.md#手数料) — 単一の料率で計算する。**実 API はペア別・maker/taker 別で、指値では符号が逆になりうる**。
  残高の推移を手数料まで含めてモックと突き合わせる設計にしていないか確認してほしい
- [残高の桁](fidelity.md#残高の桁) — 切り捨てにしたのは 1 点の観測に基づく（その値は四捨五入を否定する）。
  **推測として残るのは jpy 以外の桁と、負値の切り捨て方向**

### error code による分岐（基準 b）

- [エラーコード](fidelity.md#エラーコード) — **公式と意味が違うコードがある。** どれかは節にある。
  利用側がコードの意味を公式 `errors.md` から引く設計だと、そこで食い違う
- [数量・価格の精度](fidelity.md#数量価格の精度) — 桁に収まらない数量・価格に返すコードの選択
- [一括取消の件数上限](fidelity.md#一括取消の件数上限) — `cancel_orders` の 30 件上限は公式に明記されているが、
  **超過に返すコード（`40015`）と「1 件も取り消さない」ことは推測である。**
  31 件以上を一度に投げる利用側は分割が必要になる。**`orders_info` には同じ上限が無い**（公式どおりの非対称）
- [ペアの実在性](fidelity.md#ペアの実在性) — **発注経路のコードは実測ではなく外挿である**（照会 4 経路は実測）。
  一覧に無いペアを発注に渡す経路があるなら、ここが効いてくる
- [ペアの実在性](fidelity.md#ペアの実在性) / [ペア](fidelity.md#ペア) — **発注停止の 18 ペアへの新規発注を `70017` で断る**
  （**改訂前は成功させていた**）。コードの選択は `errors.md` の意味からの推測で、停止ペアへの発注は未実測。
  **`_btc` の 15 ペアと `mkr_jpy` / `matic_jpy` / `rndr_jpy` へ発注する経路があるなら、成功しなくなる**
  （Plan A の `btc_jpy` は含まれない）。照会と既存注文の取消は従来どおり
- [パラメータの型強制](fidelity.md#パラメータの型強制) — id の型検査は実測で確定。**推測として残るのは一部の入力と、取消 2 経路**（未実測・挙動も変えていない）
- [絞り込みパラメータの不正値](fidelity.md#絞り込みパラメータの不正値) — **`trade_history` の一部のパラメータを実装しない判断**。
  公式ドキュメントと実 API が食い違っており、公式に寄せてある。**同じ要求でモックと実 API の結果が変わる**
- [同じ名前で複数来る値](fidelity.md#同じ名前で複数来る値) — **数値を取るパラメータについては実 API の挙動を測っていない**
  （id を同名 2 本送ったときだけ実 API で確かめてある）。同名パラメータを複数送る経路が無いか確認してほしい

### 応答の形とパーサ（基準 a）

- [封筒に包まれない応答](fidelity.md#封筒に包まれない応答) — **`success` キーを持たない応答が返り得る**。
  パーサが `success` の存在を前提にしていないか
- [注文の `canceled_at`](fidelity.md#注文の-canceled_at) — **照会経路で出すかどうかが推測。** 公式の記述では決め切れない（4 節も参照）。
  **取消の判定に `canceled_at` の有無を使わないこと**
- [`expire_at`](fidelity.md#expire_at) — 常に `null` を返す（4 節も参照）
- [assets に出る資産](fidelity.md#assets-に出る資産) — 返す資産の集合に公式の根拠が無い。
  **「応答に無い＝取扱が無い」と解釈しない**
- [資産応答の固定フィールド](fidelity.md#資産応答の固定フィールド) / [信用取引・逆指値の項目](fidelity.md#信用取引逆指値の項目) —
  値が固定のフィールドと、キー自体を出さないフィールドがある。**固定値を実際の値と解釈せず、未実装の印として扱う**
- [約定の固定フィールド](fidelity.md#約定の固定フィールド) — 一部のフィールドの文字列表記に桁を仮定しないこと
- [private stream の `asset_update` のキー](fidelity.md#private-stream-の-asset_update-のキー) — **公式の表と例でキーの綴りが食い違い、
  既定の camelCase は推測である。** 両方の綴りを受けるパーサにし、`BITBANK_MOCK_STREAM_ASSET_KEYS` で切り替えて確かめること
- [private stream の注文ペイロード](fidelity.md#private-stream-の注文ペイロード) — **公式の表が英日で 5 行食い違う**（どちらにも寄せず REST の扱いのまま）。
  約定の無い注文の `executed_at`（`0`）も推測。**成行の `spot_order_new` は `FULLY_FILLED` で届く**ので、新規の通知が `UNFILLED` で始まることを前提にしないこと

### 照合（Reconcile）の前提（基準 b）

- [存在しない単一注文 ID](fidelity.md#存在しない単一注文-id) / [存在しない一括照会 ID](fidelity.md#存在しない一括照会-id) —
  **単一照会と一括照会で、存在しない id の扱いが違う。** 一括は欠落として返るので、
  利用側は再照会の上限を持つ必要がある
- [取消済み・約定済みの取消](fidelity.md#取消済み約定済みの取消) — バッチの一部だけが成立する意味の部分成功は起きない。
  一方で応答の配列が要求より短くなる場合がある（理由はその節が列挙する）。**件数の一致で成否を判定せず、`order_id` の集合で照合すること**
- [maker / taker 表示](fidelity.md#maker--taker-表示) — **注文種別だけで決め打っていて、実 API の規則は未実測。**
  表示と手数料の計算も整合しない。**表示を手数料の符号の根拠にせず、実 API で同じ値になるとも前提にしないこと**

## 4. 未確定として残っているもの

[`fidelity.md`](fidelity.md) が「未確定」「要追加確認」と明記している論点のうち、**Plan A で実装している
挙動に関わるもの**を挙げる（未実装の領域に残る未確定は 5 節）。いずれも**挙動は変えていない**。
決めるには何が要るかを添える。

| 論点 | 何が決まっていないか | 決めるのに要るもの |
| --- | --- | --- |
| [`expire_at`](fidelity.md#expire_at) | 本モックが実装する種類の注文で、実 API が非 `null` を返すか | 実 API でその種類の注文 1 件の応答を確認する |
| [注文の `canceled_at`](fidelity.md#注文の-canceled_at) | 取消済み注文の**照会**で実 API が常に返すのか、取消の応答でだけ返すのか | 公式ドキュメントでは決め切れない（英語版と日本語版で型が食い違う）。実 API で取消済み注文を照会して確認する |
| [約定の固定フィールド](fidelity.md#約定の固定フィールド) | base 資産側の手数料の文字列に、実 API が固定桁を付けるか | 実 API の約定 1 件の応答を確認する |
| [封筒に包まれない応答](fidelity.md#封筒に包まれない応答) | 壊れた JSON 本文・内部エラーに実 API が何を返すか | 実 API の応答を確認する。**公式 `errors.md` からコードを決められないので、推測では封筒に包み直していない** |
| [絞り込みパラメータの不正値](fidelity.md#絞り込みパラメータの不正値) | 公式ドキュメントと実 API が食い違うとき、どちらを正とするか | **実 API 側の意味は実測で確定済み。** 残っているのは「どちらを正とするか」という**方針の判断**で、追加の観測では決まらない |
| [解釈できない時刻を持つ state](fidelity.md#解釈できない時刻を持つ-state) | 状態ファイルの読み込み時に時刻の妥当性まで検査して fail-closed にするか | モックの内部の判断。**不変量の前提を 1 つ増やす**ことになるので、その是非 |
| [不変量をどこで担保するか](fidelity.md#不変量をどこで担保するか)（「不変量 6 の許容差」） | 残高の検査に使う許容差の根拠 | 導出も出典も残っていない。**遷移関数だけを通って誤判定になる具体例が作れていない**ので、再現が要る |

上の表は「未確定」と明記されているものだけである。**これとは別に、対応表の各節に「未実測」という
留保が散っている**（実 API を 1 回しか観測していない、発注を伴うので測っていない、など）。
どこにあるかは各節の「根拠」「本物との差異」を読むこと。

## 6. 最初に流すシナリオ

[`examples/scenario-plan-a.sh`](../examples/scenario-plan-a.sh) を最初に流してほしい。
発注 → 拘束 → `/_control/` での約定 → 残高の変化までを、`curl` だけで端から端まで通す。
**期待した状態に届かなければ終了コード 1 で止まる**ので、出力を目で読む前提になっていない。

前提:

- **`BITBANK_MOCK_CONTROL=1` でモックを起動しておく**（`/_control/` を叩くため。fill mode の既定も切り替わる）
- 叩き先の既定は `http://127.0.0.1:14000`。**別のポートで起動したときは `BITBANK_MOCK_URL`** を渡す
- 非ループバックから叩くときは `BITBANK_MOCK_CONTROL_TOKEN` も渡す
- 依存は `curl` だけ（JSON の取り出しは `sed` / `grep`）
- **先頭で状態を捨てる。** 取っておきたいシナリオがあるときは `BITBANK_MOCK_STATE_PATH` を分けること

所要時間の目安（この文書を書いた環境での実測。機械が動いている時間で、README を読む時間は含まない）:

| 手順 | 実測 |
| --- | --- |
| `git clone` | 約 1 秒 |
| `npm ci` | 約 3 秒 |
| 起動して listen まで | 約 5 秒 |
| `examples/scenario-plan-a.sh` を 1 回 | 1 秒未満 |
| clone からシナリオ完走まで | **約 40 秒** |

起動とポートの詳しい手順は [`README.md`](../README.md) の「起動」節にある。
**並列にシナリオを流すときは `BITBANK_MOCK_STATE_PATH` をシナリオごとに分けること**
（同じパスを 2 プロセスから使うと起動しない。
[`fidelity.md` の「同一状態ファイルの多重起動」](fidelity.md#同一状態ファイルの多重起動)）。

## 7. 版と改訂の所在

**[`fidelity.md`](fidelity.md) は「いま読んでいるリビジョンの `main` の挙動」を書く。**
凍結されているのは `v0.1.0` タグ（2026-09-11）が指すリビジョンだけで、対応表の側ではない。

v0.1.0 から何が変わったかは
**[`fidelity.md` の「v0.1.0 からの改訂」](fidelity.md#v010-からの改訂)** に索引がある。
何が・どう変わったかを 1 行ずつ、当該の小節へのリンク付きで並べてある。
**利用側が v0.1.0 の時点の挙動を前提に何かを書いていた場合は、まずここを突き合わせてほしい。**

- 改訂の印は本文でも「v0.1.0 からの改訂」に揃えてあるので、`grep` で拾える
- 改訂前の挙動に触れている箇所は「改訂前は…」で始まる
- パッケージの `version` は `0.1.0` のままである。**`package.json` の版数は現在の挙動を表さない**ので、
  版の判断には使わないこと
- **渡すとき・受け取るときに何を指定するか**は [`README.md`](../README.md) の「どのリビジョンを渡すか」節にある
  （タグでもブランチでもなく commit SHA を指定する。ここでは重複させない）
